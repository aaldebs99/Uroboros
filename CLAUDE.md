# CLAUDE.md

Uroboros replaces ytdl-material: a self-hosted web UI, API and downloader, one server process run
as several replicas. It is a TypeScript pnpm monorepo (packages named `@uroboros/*`) with a Hono
API and BullMQ download jobs on Valkey in the same process, Postgres through Kysely, and a React/Vite UI. Tools and tasks all come from mise
(`.mise/config.toml`).

## Definition of done

**`mise run ci` passes.** It runs exactly the gates CI runs (`ci:parity` enforces this). Do not
call a change done while any of them is red. Run a single gate with `mise run <task>`. Two of the
gates need Docker (`test` and `docker:build`) and two need the network (`check:audit` and
`lint:renovate`).

## Database and tests

The server reads `DATABASE_URL`, `VALKEY_URL` and the storage settings (`UROBOROS_STORAGE` and
its backend's variables), and the migrate entrypoint only `DATABASE_URL`; `dev:server` and
`migrate` default them to the `dev:deps` containers (RustFS for
storage).

Every replica migrates on start, as Djinn's `serve` does (`src/migrate/onStart.ts`,
`src/api/main.ts`):
it listens first, connects on a dedicated `pg.Client` (never the pool) retrying an unreachable
server within `UROBOROS_DB_STARTUP_GRACE_SECS` (0 = forever), sets `statement_timeout` and
`lock_timeout` to 0 on it (it has no client-side query timeout either), runs the migrations, and
only then attaches the database. Until then `GET /api/health` (liveness, no dependency checks)
answers 200 and `GET /api/ready` 503 `starting`; routes that need the database answer 503
`unavailable`. The job consumers start only after the database is attached, on the same pool and
connections (`src/server/main.ts`). A migration error exits 1, never ready. `mise run migrate` is the manual tool and
fails fast. There is no opt-out, and nothing else may run migrations. One replica leads at a time:
`leadAndRun` over `PgLeaderLock` (a session-level `pg_try_advisory_lock` on a dedicated
`<app>:leader` connection, pinged every 10 s). The general leader (`URO_LEAD`) runs the sweeper
(expired sessions and pending sign-ins) and the download reconcile; put singleton work there, never in a BullMQ scheduler's place (those already run once). Every
advisory lock key lives in `src/shared/lockKeys.ts`: a role is 8 ASCII bytes, a per-resource lock
`lockKey(namespace4, resource)`. Shutdown gives up leadership and stops taking jobs, drains HTTP
(`UROBOROS_SHUTDOWN_GRACE_MS`, 20 s) alongside the running jobs (25 s; a download still running 5 s
before that is cut and moved back to the queue, recording nothing and spending no attempt), bounds
the close of cut connections and the cleanup at 2 s each, and exits 1 on its own 2 s past that
budget; compose's `stop_grace_period` (35 s) covers it.
Every variable the code reads is in README's Configuration table; process code reads the
environment only through the loaders in `apps/server/src/config.ts` (the test setup is the
exception). Queries go through Kysely. A migration is a new file in
`migrations/`, created with `mise run migration:new <name>`; the runner checks every file's name
and checksum, takes an advisory lock so concurrent runners apply each file once, and refuses a
shipped file that changed. `gen` never touches a database.

`mise run test` needs Docker and no other setup. The server project's global setup
(`apps/server/test/globalSetup.ts`) starts one Postgres and one Valkey with testcontainers per
run, migrates a `uroboros_template` database and freezes it as a template. Each test that needs a
database calls `TestDb.create()`, which clones the template into a fresh database, and
`close()`s it at the end, so tests never share rows. When `UROBOROS_TEST_DATABASE_URL` and
`UROBOROS_TEST_VALKEY_URL` are set, no containers start and the template is rebuilt on the
servers they name; CI's `node` job does that with containers it starts itself. Two runs must not
share one external Postgres at the same time, because each rebuilds the template.

## Sign-in and accounts

Ported from Djinn's authentication (docs/auth.md has the decisions). Every `/api` route outside a
small public list (health, ready, info, openapi, docs, `/api/auth/methods`,
`/api/auth/local/login`, `/api/auth/oidc/*`) needs a session or an API token: `authGuard`
(`apps/server/src/auth/guard.ts`) resolves it and `currentPrincipal(c)` returns `{ userId, role,
via }`; admin routes call `requireAdmin`. Sessions are opaque random tokens in Postgres (only the
SHA-256 is stored) behind the `uroboros_session` cookie, and every cookie write needs the
`X-Uroboros-CSRF` header matching the `uroboros_csrf` cookie; bearer tokens skip CSRF but are
refused on `/api/admin`, `/api/me/tokens`, `/api/me/password`, `/api/me/sessions` and
`/api/me/push`. Local passwords are argon2id on Node's built-in `crypto.argon2`; failed sign-ins
are counted in Valkey so the limit holds across replicas. OIDC uses `openid-client` with PKCE S256
and checks ID-token signatures against the provider's JWKS; the claims sync redeems refresh tokens
under the `URO_OSYN` advisory lock, one replica at a time. An account is local or SSO, never both;
admins manage local accounts in the web app (Admin › Users), and an SSO user's role always comes
from the provider's groups. There is no account CLI. Tests sign in with `signedIn()` and
`asUser()` from `apps/server/test/auth.ts`; OIDC tests run `test/oidcIdp.ts`, a loopback HTTPS
provider (needs `openssl` on PATH).

## Downloads and storage

`docs/downloads.md` is the design. A pasted link is a `download_requests` row probed on the
`probe` queue; each video is a `downloads` row waiting on a shared **fetch key** (the
BullMQ job id on the `download` queue, `|`-separated because BullMQ refuses `:`). `dispatchFor`
dispatches at most `UROBOROS_MAX_ACTIVE_DOWNLOADS_PER_USER` per person under a per-user advisory
lock (`lockKey("DOWN", userId)`); the fetch stores the file through `MediaStore` (`s3` or organized
`filesystem` folders, one contract suite for both) and settles every waiting download in one
transaction. Progress and state go over one Valkey channel to `GET /api/downloads/events` (SSE) on
every replica; every replica also consumes the queues. The library (`docs/library.md`)
searches with Postgres full-text (`media.search`, `websearch_to_tsquery`), pages with keyset
cursors, and keeps per-person tags, watch progress and queued playlists. Tests start RustFS too
(`test/testS3.ts` gives a fresh bucket); job tests drive `@uroboros/ytdlp/testing`'s fake
binary, whose scenarios can answer per URL (`variants`). No test touches the network.

## PWA and push

The UI is an installable PWA with Web Push; `docs/push.md` is the design. The service worker is
`apps/web/src/sw/sw.ts` (vite-plugin-pwa `injectManifest`, typed by `tsconfig.sw.json` with the
WebWorker lib), registered in production builds only; dev serves a `/sw.js` that removes itself.
The manifest is static (`apps/web/public/manifest.webmanifest`). The icons are generated from
`assets/logos/uroboros-transparent.svg` by `mise run icons` and committed; never edit the PNGs by
hand. The SPA handler serves everything outside `assets/` with `no-store`. It 404s a missing file
under `/assets/` or a missing root file with an extension (`/sw.js`); every other path, dotted or
not (`/library/@john.doe`), is a client route and gets `index.html`. The service worker's
navigation fallback has no extension rule, so dotted deep links work offline too.

Every response carries Hono's secure headers and a CSP (`apps/server/src/api/security.ts`): the
SPA's allows scripts from its own origin only, so `index.html` has no inline script (the
pre-paint theme script is `public/theme-init.js`), and `/api/docs` has its own, serving the
pinned `swagger-ui-dist` from the bundle rather than a CDN. `/api/*` refuses bodies over
`UROBOROS_BODY_LIMIT_BYTES` (64 KiB) with `payload_too_large`.

Sending lives in `apps/server/src/push/` (payload builder, allowlist, sender, `Pusher`), so the
`notify` queue's consumer can reuse it; a feature that notifies enqueues there rather than sending
from a request. No test may reach a real push service: use `apps/server/test/pushStub.ts`. Devices
belong to the signed-in user, `currentPrincipal(c)` (`apps/server/src/api/principal.ts`). The server reads `UROBOROS_PUBLIC_BASE_URL` (push is on only when it is
https), `UROBOROS_PUSH_SUBJECT`, `UROBOROS_VAPID_PUBLIC_KEY` with `UROBOROS_VAPID_PRIVATE_KEY`
(both or neither; without them the first replica generates a pair into `vapid_keys`),
`UROBOROS_PUSH_ALLOWED_HOSTS` and `UROBOROS_PUSH_MAX_DEVICES` (10). A new variable goes into
`config.ts`, `compose.yaml` and README's Configuration table together.

## Principles

**Ratchets only tighten.** Never raise a cap, and never add an exception entry to get a red gate
through. Bring the code under the cap instead: split the file, extract a function, or move code to
a sibling module. When a frozen number in `tools/ratchet/frozen.json` improves, lower it in the
same commit, because slack fails the gate too. Cognitive complexity is measured by sonarjs with
limits of 25 per function and a sum of 200 per file; files stop at 1000 lines. Details are in
`docs/ratchets.md`.

**Wire types live only in the contract.** Every shape that crosses HTTP (bodies, errors and
everything they contain) is a zod schema in `packages/contract`. The server's routes use those
schemas for validation and OpenAPI, and the web client parses every response with them; neither
side declares an API JSON shape of its own. Errors are `ApiErrorBody` (`{ code, message }`), with
`code` an `ApiErrorCode` and its status in `apiErrorStatus`. Branch on contract enums
exhaustively so a new variant breaks `tsc`. After a contract change, run `mise run gen` and commit
`api/openapi.json`; never hand-edit it.

**Entrypoints have no import-time side effects.** A module that does work when imported cannot be
tested or bundled safely. Each process starts from a two-line wrapper in `apps/server/src/bin/`
that calls an exported `main()` and sets `process.exitCode`; everything else only exports.

**Pins move together.** node and pnpm are each pinned in several files (mise, `package.json`'s
`engines`, `packageManager` and `devEngines`, the Dockerfile ARGs), and the 3-day supply-chain
soak is set in both `.renovaterc.json5` and `pnpm-workspace.yaml`. `ratchet:pins` checks they
agree. Change every copy in one commit, and never lower the soak. Dependencies are pinned
exactly. After editing `[tools]`, run `mise lock` for every platform. Container images are
pinned by exact tag and digest; the third-party ones (Postgres, Valkey, RustFS, Caddy) only in
`compose.yaml`, which the test setup (`apps/server/test/composeImage.ts`), CI and the smoke test
read through `scripts/image/compose-image.sh`, so Renovate's one bump moves them all.

**Task bodies are POSIX.** They run under `sh` (dash on Debian runners): no `[[ ]]`, no
`<(...)`, no `pipefail`. Anything longer belongs in a script under `scripts/`.

**Migrations stay compatible with the previous release (from the first release on).** Migrations are applied by the first new
replica to start, while replicas from the previous release are still serving, and a rollback runs old code on the new schema, so
every migration must work with the code of the release before it. Change a schema in steps across releases:
expand (add the nullable column, the new table), migrate (code writes both, backfill), then
contract (drop the old shape) only once no running release reads it. Never rename or drop in the
same release that stops using something. Each file runs inside one transaction, so statements
that cannot run in a transaction, such as `CREATE INDEX CONCURRENTLY`, are not supported: use a
plain `CREATE INDEX` while the table is small, and add runner support before the first table
large enough to need one.

**Pre-release: one schema file, edited in place.** There are no deployed databases yet, so the whole
schema lives in `migrations/20261122000000_schema.sql` and schema changes edit that file. Do not add
migration files or expand/contract steps until the user says otherwise. After changing it, reset
local databases: `mise run docker:down`, then `docker volume rm uroboros_postgres-data` (tests build
a fresh database every run). From the first release on, the rules below apply: migrations are
named `<YYYYMMDDHHMMSS>_<logical_name>.sql` (a real UTC creation datetime plus a descriptive
snake_case name, never sequential numbers), created with `mise run migration:new <name>`, and a
shipped migration is never edited.

**yt-dlp is the only downloader.** Never youtube-dl, youtube-dlc or another fork, and no
downloader setting or fallback. Only the job consumers spawn yt-dlp and ffmpeg (never a request
handler); the HTTP side only checks profiles against `@uroboros/ytdlp/flags`. The image pins yt-dlp with hashes in `scripts/image/requirements.txt`, and the smoke test
fails if any other downloader is on the image. Its ffmpeg is yt-dlp's GPL build, taken
from the mirror image `code.example.com/aaldebs99/ffmpeg-ytdlp` (built in the upstream-builder
repo), pinned by tag and index digest in the Dockerfile's `ffmpeg` stage and bumped by Renovate
(`.renovaterc.json5`, and the registry credentials in `renovate.yml`). The registry is private:
the `docker:*` tasks need `docker login code.example.com`, and `ci.yml`'s `images` job logs in
with `REGISTRY_TOKEN`. The image ships the licences and notices under
`/usr/share/licenses/ffmpeg/`; the source stays in the mirror (`/usr/src/ffmpeg-ytdlp/`), and
`THIRD_PARTY.md` says what that means for distributing the image. Do not swap the build without
updating both.

**RustFS is the S3 server** for local stacks and tests, never MinIO.

**Superpowers files stay local.** `.superpowers/` and `docs/superpowers/` are gitignored and never
committed; do not `git add` anything under them.

## Forge and release

The repository lives on Forgejo at https://code.example.com/aaldebs99/Uroboros. The workflows
run on Forgejo Actions with the Gitea runner's labels (`small`, `big`, `big-dind` and so on,
listed in `.github/actionlint.yaml`). They carry no `permissions:` blocks, because Forgejo ignores
the field and warns about it; zizmor's audit of it is off in `.github/zizmor.yml` for that reason.
Every CI step is `run: mise run <task>`, and the `CI` job is the one required status check.

Releases are proposed, not pushed. On every push to main, `release-pr.yml` first publishes the
version `apps/server/package.json` carries if it has no release yet (the 0.0.0 placeholder is
never released), then asks git-cliff for the next version from the conventional commits since the
last tag and rebuilds the `release/next` branch with one `chore(release): X.Y.Z` commit. That
commit stamps the version into both `package.json` files and `api/openapi.json`, and prepends
the CHANGELOG section. Merging the PR cuts the release. The release
event triggers `release.yml`, which builds the image, runs `scripts/image/smoke-test.sh` against
it, and only then pushes `<REGISTRY>/aaldebs99/uroboros:X.Y.Z`, `:X.Y` and `:latest`. Every push to
main also publishes `:main`, without the smoke test. Only feat, fix, perf, revert, deps and breaking commits
cut a release, so tooling changes belong under ci, chore or build. PR titles must be
conventional commits (`pr-title.yml`), because the squash subject feeds the changelog.

| Name                        | Kind     | Used by                 | What it is                                                                                                                                |
| --------------------------- | -------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `REGISTRY`                  | variable | `release.yml`           | The registry host the images go to, e.g. `code.example.com`.                                                                          |
| `REGISTRY_TOKEN`            | secret   | `release.yml`, `ci.yml` | An access token of `aaldebs99` scoped `write:package`; only the namespace owner may push. `ci.yml` reads the ffmpeg mirror image with it. |
| `RELEASE_PLEASE_TOKEN`      | secret   | `release-pr.yml`        | The release bot's token (`write:repository`, `write:issue`, `read:user`), so its PRs and releases trigger workflows.                      |
| `RENOVATE_TOKEN`            | secret   | `renovate.yml`          | The Renovate bot's token (`write:repository`, `write:issue`, `read:user`, `read:organization`).                                           |
| `RENOVATE_GITHUB_COM_TOKEN` | secret   | `renovate.yml`          | A github.com token with no scopes, for looking up GitHub-hosted actions and tools.                                                        |

Accepted risk: `REGISTRY_TOKEN` can write packages, yet `ci.yml` uses it to pull, so builds of same-repository pull requests, Renovate's branches included, can read a write-capable registry token; a read-only token would remove that risk. Fork PRs get no secrets, so their `images` job always fails at the ffmpeg pull.
