# CLAUDE.md

Uroboros replaces ytdl-material: a self-hosted web UI, API and download workers. It is a
TypeScript pnpm monorepo (packages named `@uroboros/*`) with a Hono API, BullMQ workers on
Valkey, Postgres through Kysely, and a React/Vite UI. Tools and tasks all come from mise
(`.mise/config.toml`).

## Definition of done

**`mise run ci` passes.** It runs exactly the gates CI runs (`ci:parity` enforces this). Do not
call a change done while any of them is red. Run a single gate with `mise run <task>`. Two of the
gates need Docker (`test` and `docker:build`) and two need the network (`check:audit` and
`lint:renovate`).

## Layout

| Path                  | What it is                                                                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/server`         | `@uroboros/server`: the api (`src/api`), the worker (`src/worker`), the migration runner (`src/migrate`) and the OpenAPI generator (`src/gen`).                                 |
| `apps/server/src/bin` | The four entrypoints, `api.ts`, `worker.ts`, `migrate.ts` and `gen.ts`. Each is a two-line wrapper that calls a side-effect-free `main()`. tsdown bundles them to `dist/*.mjs`. |
| `apps/web`            | `@uroboros/web`: React, TanStack Router and Query, Tailwind. Talks to the api through `src/api/client.ts`, which validates every response against the contract.                 |
| `packages/contract`   | `@uroboros/contract`: the zod schemas for everything that crosses HTTP (bodies, errors, enums). The server's OpenAPI routes and the web client both import from here.           |
| `tools/ratchet`       | `@uroboros/ratchet`: the ratchets and `ci-parity`, TypeScript run on node's type stripping. Its frozen numbers are in `tools/ratchet/frozen.json`.                              |
| `migrations/`         | Forward-only SQL migrations, applied by the migrate entrypoint (a one-shot compose service, a Helm hook Job in Kubernetes). The api never migrates.                             |
| `api/openapi.json`    | Generated by `mise run gen` and committed. `check:gen` fails on drift.                                                                                                          |
| `chart/uroboros`      | The Helm chart: api Deployment, worker Deployment, migrate hook Job, worker egress NetworkPolicy. `ci/*-values.yaml` are the renders `lint:chart` validates.                    |
| `compose.yaml`        | The production-shaped local stack: Postgres, Valkey, RustFS, migrate, two api replicas behind Caddy, two workers.                                                               |
| `compose.dev.yaml`    | The dev overlay: the api from source with `tsx watch`, and loopback ports for Postgres, Valkey and RustFS.                                                                      |
| `Dockerfile`          | One build stage, two runtime targets: `api` (distroless, the default) and `worker` (Debian slim with yt-dlp's static ffmpeg and the pinned yt-dlp).                             |
| `scripts/image`       | The worker image's install scripts, yt-dlp's hashed `requirements.txt`, and `smoke-test.sh`, which proves both images work.                                                     |
| `scripts/release`     | `propose.sh`, `publish.sh` and their `lib.sh`: the release PR and the release cut that `.github/workflows/release-pr.yml` runs.                                                 |
| `.github/workflows`   | `ci.yml` (the gates), `pr-title.yml`, `release-pr.yml`, `release.yml` (images) and `renovate.yml`.                                                                              |

Every host port has an override: `UROBOROS_PORT` (Caddy, 18080), `UROBOROS_POSTGRES_PORT`
(15432), `UROBOROS_VALKEY_PORT` (16379), `UROBOROS_S3_PORT` and `UROBOROS_S3_CONSOLE_PORT`
(19000, 19001), `UROBOROS_UI_PORT` (18173) and `UROBOROS_BIND` for a host-run api (default
`127.0.0.1:18081`). Inside containers the services keep their own ports.

## Database and tests

The api and the worker read `DATABASE_URL` and `VALKEY_URL`; `dev:api` and `dev:worker` default
them to the `dev:deps` containers. Queries go through Kysely. A migration is a new file in
`migrations/`, created with `mise run migration:new <name>`; the runner checks every file's name
and checksum, takes an advisory lock so concurrent runners apply each file once, and refuses a
shipped file that changed. `gen` never touches a database.

`mise run test` needs Docker and no other setup. The server project's global setup
(`apps/server/test/globalSetup.ts`) starts one Postgres and one Valkey with testcontainers per
run, migrates a `uroboros_template` database and freezes it as a template. Each test that needs a
database calls `TestDb.create()`, which clones the template into a fresh database, and
`close()`s it at the end, so tests never share rows. When `UROBOROS_TEST_DATABASE_URL` and
`UROBOROS_TEST_VALKEY_URL` are set, no containers start and the template is rebuilt on the
servers they name; CI's `node` job does that with containers it starts itself. Two runs must not
share one external Postgres at the same time, because each rebuilds the template.

## PWA and push

The UI is an installable PWA with Web Push; `docs/push.md` is the design. The service worker is
`apps/web/src/sw/sw.ts` (vite-plugin-pwa `injectManifest`, typed by `tsconfig.sw.json` with the
WebWorker lib), registered in production builds only; dev serves a `/sw.js` that removes itself.
The manifest is static (`apps/web/public/manifest.webmanifest`). The icons are generated from
`assets/logos/uroboros-transparent.svg` by `mise run icons` and committed; never edit the PNGs by
hand. The SPA handler serves everything outside `assets/` with `no-store`. It 404s a missing file
under `/assets/` or a missing root file with an extension (`/sw.js`); every other path, dotted or
not (`/library/@john.doe`), is a client route and gets `index.html`. The service worker's
navigation fallback has no extension rule, so dotted deep links work offline too.

Sending lives in `apps/server/src/push/` (payload builder, allowlist, sender, `Pusher`), so the
worker's `notify` queue can reuse it; a feature that notifies enqueues there rather than sending
from a request. No test may reach a real push service: use `apps/server/test/pushStub.ts`. Devices
belong to `currentPrincipal(c)` (`apps/server/src/api/principal.ts`), a fixed local principal
until Users and SSO replace it. The api reads `UROBOROS_PUBLIC_BASE_URL` (push is on only when it is
https), `UROBOROS_PUSH_SUBJECT`, `UROBOROS_VAPID_PUBLIC_KEY` with `UROBOROS_VAPID_PRIVATE_KEY`
(both or neither; without them the first replica generates a pair into `vapid_keys`),
`UROBOROS_PUSH_ALLOWED_HOSTS` and `UROBOROS_PUSH_MAX_DEVICES` (10). A new variable goes into
`config.ts`, `compose.yaml` and the chart (values, schema, templates) together.

## Principles

**Ratchets only tighten.** Never raise a cap, and never add an exception entry to get a red gate
through. Bring the code under the cap instead: split the file, extract a function, or move code to
a sibling module. When a frozen number in `tools/ratchet/frozen.json` improves, lower it in the
same commit, because slack fails the gate too. Cognitive complexity is measured by sonarjs with
limits of 25 per function and a sum of 200 per file; files stop at 1000 lines. Details are in
`docs/ratchets.md`.

**Wire types live only in the contract.** Every shape that crosses HTTP (bodies, errors and
everything they contain) is a zod schema in `packages/contract`. The server's routes use those
schemas for validation and OpenAPI, and the web client parses every response with them; neither
side declares an API JSON shape of its own. Errors are `ApiErrorBody` (`{ code, message }`), with
`code` an `ApiErrorCode` and its status in `apiErrorStatus`. Branch on contract enums
exhaustively so a new variant breaks `tsc`. After a contract change, run `mise run gen` and commit
`api/openapi.json`; never hand-edit it.

**Entrypoints have no import-time side effects.** A module that does work when imported cannot be
tested or bundled safely. Each process starts from a two-line wrapper in `apps/server/src/bin/`
that calls an exported `main()` and sets `process.exitCode`; everything else only exports.

**Pins move together.** node and pnpm are each pinned in several files (mise, `package.json`'s
`engines`, `packageManager` and `devEngines`, the Dockerfile ARGs), and the 3-day supply-chain
soak is set in both `.renovaterc.json5` and `pnpm-workspace.yaml`. `ratchet:pins` checks they
agree. Change every copy in one commit, and never lower the soak. Dependencies are pinned
exactly. After editing `[tools]`, run `mise lock` for every platform.

**Task bodies are POSIX.** They run under `sh` (dash on Debian runners): no `[[ ]]`, no
`<(...)`, no `pipefail`. Anything longer belongs in a script under `scripts/`.

**Migrations are named `<YYYYMMDDHHMMSS>_<logical_name>.sql`:** a real UTC creation datetime
plus a descriptive snake_case name, never sequential numbers. Create them with
`mise run migration:new <name>`. They are forward-only: a shipped migration is never edited, and a
change is always a new file.

**yt-dlp is the only downloader.** Never youtube-dl, youtube-dlc or another fork, and no
downloader setting or fallback. The api never spawns yt-dlp or ffmpeg; only workers do. The
worker image pins yt-dlp with hashes in `scripts/image/requirements.txt`, and the smoke test
fails if any other downloader is on the image. The worker's ffmpeg is yt-dlp's GPL build from
`yt-dlp/FFmpeg-Builds`, pinned by release tag and checksums digest (`FFMPEG_TAG`,
`FFMPEG_CHECKSUMS_SHA256` in the Dockerfile, installed by `scripts/image/install-ffmpeg.sh`).
It ships with its licence and a `SOURCE.md` under `/usr/share/licenses/ffmpeg/`; `THIRD_PARTY.md`
lists what each image carries. Do not swap the build without updating both.

**RustFS is the S3 server** for local stacks and tests, never MinIO.

**Superpowers files stay local.** `.superpowers/` and `docs/superpowers/` are gitignored and never
committed; do not `git add` anything under them.

## Forge and release

The repository lives on Forgejo at https://code.example.com/aaldebs99/Uroboros. The workflows
run on Forgejo Actions with the Gitea runner's labels (`small`, `big`, `big-dind` and so on,
listed in `.github/actionlint.yaml`). They carry no `permissions:` blocks, because Forgejo ignores
the field and warns about it; zizmor's audit of it is off in `.github/zizmor.yml` for that reason.
Every CI step is `run: mise run <task>`, and the `CI` job is the one required status check.

Releases are proposed, not pushed. On every push to main, `release-pr.yml` first publishes the
version `apps/server/package.json` carries if it has no release yet (the 0.0.0 placeholder is
never released), then asks git-cliff for the next version from the conventional commits since the
last tag and rebuilds the `release/next` branch with one `chore(release): X.Y.Z` commit. That
commit stamps the version into both `package.json` files, `api/openapi.json` and the chart's
`appVersion`, and prepends the CHANGELOG section. Merging the PR cuts the release. The release
event triggers `release.yml`, which builds both images, runs `scripts/image/smoke-test.sh`
against them, and only then pushes `<REGISTRY>/aaldebs99/uroboros:X.Y.Z`, `:X.Y` and `:latest`,
with the worker under the same tags plus `-worker`. Every push to main also publishes `:main` and
`:main-worker`, without the smoke test. Only feat, fix, perf, revert, deps and breaking commits
cut a release, so tooling changes belong under ci, chore or build. PR titles must be
conventional commits (`pr-title.yml`), because the squash subject feeds the changelog.

| Name                        | Kind     | Used by          | What it is                                                                                                           |
| --------------------------- | -------- | ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| `REGISTRY`                  | variable | `release.yml`    | The registry host the images go to, e.g. `code.example.com`.                                                     |
| `REGISTRY_TOKEN`            | secret   | `release.yml`    | An access token of `aaldebs99` scoped `write:package`; only the namespace owner may push.                            |
| `RELEASE_PLEASE_TOKEN`      | secret   | `release-pr.yml` | The release bot's token (`write:repository`, `write:issue`, `read:user`), so its PRs and releases trigger workflows. |
| `RENOVATE_TOKEN`            | secret   | `renovate.yml`   | The Renovate bot's token (`write:repository`, `write:issue`, `read:user`, `read:organization`).                      |
| `RENOVATE_GITHUB_COM_TOKEN` | secret   | `renovate.yml`   | A github.com token with no scopes, for looking up GitHub-hosted actions and tools.                                   |
